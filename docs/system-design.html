The decision that makes it scale: cameras record in copy (remux) mode — FFmpeg writes the camera's already-compressed H.264/H.265 straight to disk, no re-encoding. Per-camera CPU is tiny; the real limits are disk throughput and network bandwidth.

Recording — the priority path

  1. Camera → FFmpeg input
    RTSP over TCP; in copy mode packets pass through with no re-encode.
  2. Segment muxer → disk
    -f segment -segment_time 15m -strftime rotates into time-named MP4 files; a crash loses at most one in-progress segment.
  3. Completed filename → parent
    -segment_list pipe:8 emits each finished file to catchNewSegmentNames.
  4. File → DB row
    insertCompletedVideo stat()s the file and inserts a Videos row (status:1), and pushes video_build_success live.
  5. Safety nets
    An orphan scan reclaims any file lacking a row; a stall watchdog restarts a camera that stops producing segments within 1.3× the segment length; fatalError applies escalating restart backoff.

Why three mechanisms, not one

Recording is the product. A single "segment finished" signal is not enough for a security system — so a file on disk is reconciled to a DB row by three independent paths (live pipe, orphan scan, stall-restart). This redundancy is deliberate, and a real orphaned-process leak in the restart path was found and fixed during hardening.

The honest ceiling

The cluster multiplies raw camera capacity across nodes, but every child funnels its database queries, its recorded files, and its live traffic through the single master. So the practical limit toward thousands is the master's event loop, disk, and NIC — not the number of children. Reaching true thousands is a deliberate re-architecture, not a config flag.

Whatever the count: it is only proven by a staged load test (40 → 80 → 150 → beyond) with a camera simulator. The hardware won't be the surprise — per-process behavior under full count is what the test validates.

The pluggable-AI contract

The entire integration surface an external GPU AI server touches is two things: read camera frames over RTSP, and report a detection with one HTTP call.

GET /<API_KEY>/motion/<GROUP>/<MONITOR>?reason=Fire&confidence=92&name=evt

reason is an opaque label the VMS records and pushes live; the dashboard's event registry styles any type with a neutral default. A new detection — crowd, PPE, anything — appears with zero VMS code change. That is what makes one VMS serve many clients.
